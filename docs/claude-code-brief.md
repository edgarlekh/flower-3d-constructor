## 1. Что это за продукт

Веб-инструмент, который показывает паре или декоратору, как будет выглядеть свадебный цветочный декор, и сразу считает цену. Позже — расстановка в 3D-зале и интерактивный показ заказчику.

Полная человеческая концепция — в файле `docs/concept.md` (я его создам из этого брифа). Здесь — техническая выжимка.

## 2. Незыблемые принципы — нарушать нельзя

1. **Ручная расстановка — сердце продукта.** Автосборка даёт только стартовый вариант. Дальше пользователь берёт каждый цветок и двигает его пальцем/мышью туда, куда хочет. Любой механизм, который не даёт подвинуть отдельный элемент руками, — неправильный. Это применимо и к букету, и к столу, и позже к арке: везде один и тот же движок «взять объект и поставить куда хочу».

2. **Реальные сантиметры.** Сцена живёт в сантиметрах. Каждый объект каталога несёт реальные габариты. Стол 90 см — это 90 см. Ваза 35 см в диаметре реально не влезает между двумя тарелками на столе 90 см, и система это показывает.

3. **Размер задаётся вводом одного числа.** Фотография не содержит масштаба — нейросеть строит форму, не размер. Поэтому: модель безразмерна (нормализована), пользователь вводит ОДИН реальный размер (обычно высоту), система масштабирует модель и выводит остальные габариты из пропорций. Не пытаться «вытащить размер из модели» автоматически — его там нет.

4. **Модели лёгкие.** Всё грузится быстро в мобильном браузере. Геометрия квантуется, текстуры ужимаются. В прототипе уже отработан пайплайн упаковки GLB в компактный base64-JS.

5. **Каталог — правда о товаре.** Цветок в каталоге = цветок, который реально привезут. Никаких «похожих». Это продуктовое обещание, оно влияет на доверие.

## 3. Что уже готово (перенести из прототипа)

В `/mnt/user-data/outputs/` пользователя лежат рабочие прототипы. Актуальный — **bouquet-builder-v14.html**. В нём уже есть:

- конструктор букета: каталог-корзина (набираешь количество стеблей → собирается 3D-букет)
- раскладка по ролям (accent/mass/filler/green), золотой угол, купол Fibonacci, детерминированный ГПСЧ
- смета с разбивкой: цветы / упаковка / работа
- реальная модель розы (vertex colours) и две вазы (GLB с фото), посадка букета в вазу, выбор вазы
- стебли выходят из горловины вертикально, расходятся выше среза
- камера для телефона: один палец — орбита, два — зум/pan, инерция, кадрирование по охватывающей сфере, ограничение углов
- предупреждения (не влезает в горловину и т.п.)

**Важно про текстуры GLB:** в three.js для моделей из TRELLIS/Meshy обязательно `texture.flipY = false` — иначе развёртка ложится зеркально (в прототипе этот баг уже отловлен и исправлен, не повторять).

Файл v14 — единый HTML. Первая инженерная задача — не тащить его как есть, а аккуратно разложить на модули (см. раздел 5).

## 4. Стек и ограничения

- Чистый фронтенд: HTML + JS, **three.js r128** (как в прототипе), без сборщика на старте
- Хостинг: Cloudflare Pages, деплой из корня репо, автопубликация по push
- Без бэкенда на старте. Каталог — статический JS-файл. БД появится позже
- Модели — GLB, упакованные в компактный формат (пайплайн в `scripts/`)
- Никаких тяжёлых фреймворков без явного согласования. Причина — скорость на телефоне и простота поддержки
- Код и комментарии — понятные. Пользователь будет читать и просить объяснить

│       └── models/              ← .glb файлы

│   ├── pack-model.py            ← GLB → компактный JS (из прототипа)

## 6. Модель данных каталога

Каждый объект несёт габариты в сантиметрах и роль. Пример `catalog.js`:

```javascript
window.CATALOG = [
  {
    id: 'rose-red',
    type: 'flower',
    name: 'Роза красная',
    role: 'mass',              // accent | mass | filler | green
    bloom_cm: 7,               // диаметр цветка
    stem_cm: 45,               // длина стебля
    price: 0.85,               // за стебель, $
    model: 'models/rose-red.js',
    thumb: 'models/rose-red-thumb.jpg'
  }
];

window.VASES = [
  {
    id: 'vase-tall',
    type: 'vase',
    name: 'Ваза высокая',
    height_cm: 30,             // ЕДИНСТВЕННЫЙ введённый вручную размер
    // остальные габариты выводятся из пропорций модели:
    neck_ratio: 0.19,          // радиус горловины в долях высоты
    width_ratio: 0.51,         // ширина в долях высоты
    price: 45,
    model: 'models/vase-tall.js'
  }
];

// Позже: window.TABLES, window.TEXTILES, window.VENUES
```

Ключевое: `height_cm` — введён руками. `neck_ratio`, `width_ratio` — посчитаны из модели пайплайном. Так реализуется принцип «одно число вручную, остальное из пропорций».

## 7. Дорожная карта — строго по порядку

### ЭТАП 0 — Скелет (первая задача, делаем сейчас)
- создать структуру папок из раздела 5
- `.gitignore`, `README.md`
- `index.html` — простой честный лендинг: что это, для кого, одна кнопка «Собрать букет» → `constructor.html`
- `constructor.html` — заглушка «скоро»
- закоммитить, запушить, убедиться что открывается на `.pages.dev`
**Цель этапа:** живой адрес с лендингом. Проверяем всю связку.

### ЭТАП 1 — Перенос конструктора (ядро MVP)
- разложить v14 на модули из раздела 5
- вынести каталог в `catalog.js` с полной моделью данных (раздел 6)
- проверить: букет собирается, вазы работают, смета считается, камера удобна на телефоне
**Цель:** конструктор из прототипа живёт на сайте в чистой структуре.

### ЭТАП 2 — Ручное перетаскивание (главная фича MVP)
- режим редактирования: захват отдельного цветка в 3D, перемещение, возврат
- начать можно с ограниченной версии (двигать 2-3 цветка) как доказательство механики, затем полноценно
- это тот самый движок «взять и поставить», на котором дальше держится всё
**Цель:** декоратор может подвинуть цветок туда, куда хочет. Без этого продукт для декоратора мёртв.

### ЭТАП 3 — Пополнение каталога
- скрипт `generate-models.py`: папка фото → GLB (TRELLIS 2 / Meshy)
- `pack-model.py`: GLB → компактный JS (перенести из прототипа, он готов)
- прогнать 12-14 позиций: цветы, зелень, вазы, пара предметов
**Цель:** сцена, которой не стыдно показать скептикам.

### ЭТАП 4 и дальше (НЕ в MVP, не начинать без отдельной команды)
- расстановка в 3D-зале: столы, стулья, текстиль, размеры на экране, проверки «влезает/тесно», авто-план рассадки
- показ заказчику: ссылка, хождение по залу (клик по полу → камера едет), вид с места гостя (камера на 115 см)
- арки и большие конструкции (тот же движок расстановки по каркасу)
- каталоги поставщиков, площадки, оплата, договоры, роли, языки/валюты

## 8. Чего НЕ делать в MVP (сознательно отложено)

Не тащить, даже если попросят «заодно»:
- бэкенд, база данных, личные кабинеты, авторизация
- оплата внутри платформы
- регистрация поставщиков/прокатчиков/площадок
- международность: языки, валюты, единицы
- мобильное приложение (только сайт)
- фотореализм рендера (прототип честно подписан «логика, не графика»)

Если задача тянет за собой что-то из этого списка — остановись и спроси пользователя.

## 9. Как работаем

- маленькими шагами: один экран / одна фича за подход, коммит, проверка на живом адресе
- после значимого изменения — `git add`, `git commit` с внятным сообщением, `git push origin main`
- прототипы пользователя лежат в `/mnt/user-data/outputs/` — можно смотреть и переносить из них код
- при развилке в архитектуре — короткое объяснение вариантов пользователю простыми словами, а не молчаливый выбор
- беречь два незыблемых: ручная расстановка и реальные размеры. Любое решение сверяется с ними
